A UUID like `01a15c4c-c8ee-7439-aa40-3bf8e7fa6b21` is a fine database key and a
clumsy URL. It's 36 characters long, uses only hex digits, and nobody can read it out over the phone.
For share links, invite codes, short slugs or file names you usually want
something shorter and friendlier.

[NanoID](https://github.com/ai/nanoid) is the popular answer: random IDs from a
chosen alphabet, at a chosen length. This guide covers how to pick both, using
the <ToolLink tool="nanoid" />.

## Same idea, different packaging

A random identifier is just *N* random bits written in some alphabet. The safety
of the ID depends only on how many random bits it carries:

| Format | Example | Length | Random bits |
|---|---|---|---|
| UUID v4 | `9f1c2b7e-4d3a-4e8b-a1f0-6c2d9e7b5a13` | 36 | 122 |
| NanoID (default) | `V1StGXR8_Z5jdHi6B-myT` | 21 | 126 |
| NanoID, 12 chars | `HeEaoGHaVSpj` | 12 | 72 |

NanoID's default (21 characters from a 64-character URL-safe alphabet) carries
*more* randomness than a v4 UUID in 15 fewer characters, because each character
holds 6 bits instead of hex's 4. Shorter IDs are a deliberate trade-off,
and the math tells you how far you can go.

## How short is too short?

The question to ask is: **how many IDs can I create before a collision becomes
likely?** By the birthday bound, an ID with *b* random bits reaches a 1% chance
of *any* collision after roughly `0.14 × 2^(b/2)` IDs.

| Alphabet | Size | Bits | IDs before a 1% collision chance |
|---|---|---|---|
| `url` (64 chars) | 21 | 126 | ~1.3 × 10¹⁸ |
| `url` | 16 | 96 | ~40 trillion |
| `url` | 12 | 72 | ~10 billion |
| `url` | 10 | 60 | ~150 million |
| `url` | 8 | 48 | ~2.4 million |
| `nolookalikes` (57) | 12 | 70 | ~5 billion |
| `lowercase` (36) | 16 | 83 | ~400 billion |
| `numbers` (10) | 12 | 40 | ~140 thousand |

How to read it: if you'll create a few thousand invite codes a year, 8–10
characters are plenty. For public links to millions of documents, use at least 12–16.
When in doubt, keep the default of 21. Bits are cheap.

<Callout type="tip">
A collision isn't always a disaster: if your database has a unique index, you can
catch the duplicate-key error and retry. It's still better to pick a length where
that almost never happens.
</Callout>

Short IDs are also easier to **guess**. If the ID alone grants access to something
(for example, an unlisted share link), keep it long (≥ 21 characters) and add rate
limiting. Anything that protects real secrets should be a proper 128- to 256-bit token.

## Choosing an alphabet

The generator supports six named alphabets:

| Name | Characters | Use it for |
|---|---|---|
| `url` (default) | `A-Z a-z 0-9 _ -` (64) | URLs, keys, anything machine-read |
| `alphanumeric` | `A-Z a-z 0-9` (62) | When `_` and `-` cause trouble |
| `lowercase` | `a-z 0-9` (36) | Case-insensitive systems: DNS labels, some file systems |
| `nolookalikes` | alphanumeric minus `0 O 1 l I` (57) | Codes people read, type or dictate |
| `numbers` | `0-9` | Numeric-only fields, PIN-style codes |
| `hex` | `0-9 a-f` | Systems expecting hex |

A good example of why the alphabet matters: an ID that ends up in a
case-insensitive context (a subdomain, an email address, a Windows file name)
can lose its uniqueness if it relies on upper/lower case. Use `lowercase` there,
and add length to make up for the smaller alphabet.

## The trouble with `-` and `_` at the edges, and `safeEnds`

The default URL alphabet includes `-` and `_`. They're perfectly valid in URLs, but at
the **start or end** of an ID they cause small, annoying problems:

- An ID starting with `-`, like `-xY3…`, gets parsed as a **command-line flag**:
  `git checkout -xY3…` or `rm -xY3…` fail in confusing ways.
- **Double-click selection** in most editors and terminals stops at a leading or
  trailing `-`, so people copy a truncated ID.
- Some Markdown renderers and chat apps treat a trailing `_` as formatting.

The WebTools generator has a `safeEnds` option for this. It keeps the first and
last characters alphanumeric while the middle still uses the full alphabet. It costs
almost nothing: about 0.1 bit out of 126 for a default-size ID.

## Generate from the API

```bash
curl -s '@@API_BASE@@/api/v1/nanoid?count=2&size=12&safeEnds=true'
```

```json
{
  "alphabet": "url",
  "size": 12,
  "safeEnds": true,
  "count": 2,
  "ids": ["HeEaoGHaVSpj", "oAR1SdA9qg2n"]
}
```

| Parameter | Values | Default |
|---|---|---|
| `count` | `1`–`10` | `1` |
| `size` | `2`–`255` | `21` |
| `alphabet` | `url`, `alphanumeric`, `lowercase`, `numbers`, `hex`, `nolookalikes` | `url` |
| `safeEnds` | `true` / `false` | `false` |

AI agents get the same thing through the `generate_nanoid`
[MCP tool](/blog/mcp-server-for-ai-agents). For example, *"give me 5 invite codes,
10 characters, no confusing letters"* becomes
`{ "count": 5, "size": 10, "alphabet": "nolookalikes" }`.

Under the hood, characters are drawn with `crypto.getRandomValues` and **rejection
sampling**. A naive `byte % alphabetLength` would slightly favour some
characters whenever the alphabet size isn't a power of two (as with 57 or 62).

## NanoID or UUID? A decision guide

- **Database primary key** → [UUID v7](/blog/uuid-v4-vs-v7). It sorts by time, has a
  native 16-byte column type, and every tool understands it. If you'd rather have a
  shorter sortable ID, see [ULID vs UUID v7](/blog/ulid-vs-uuid-v7).
- **Public URL or share link** → NanoID, 16–21 characters, `url` alphabet with
  `safeEnds`.
- **Code a human types or reads aloud** (invites, vouchers) → NanoID with
  `nolookalikes`, 8–12 characters, and a unique index with retry.
- **Case-insensitive context** (subdomains, file names) → NanoID `lowercase`, 16+
  characters.
- **Interop with systems that expect UUIDs** → UUID. Don't fight the schema.
- **Secrets** (API keys, reset tokens) → neither tool is the point here. Use at least
  32 bytes from a CSPRNG and store only a hash.

A pattern that works well: a UUID v7 as the internal primary key, plus a NanoID
column (with a unique index) for the public-facing identifier.
