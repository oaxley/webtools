Two login forms. The first asks for a password. The second asks for the same
password, then for six digits from an app on your phone. The extra field looks
small, but the two secrets behave very differently.

A **password** is a secret you *send*: every time you log in, the secret itself
goes to the server. A **TOTP code** is *computed from* a secret that never leaves
your phone after setup, and it expires 30 seconds later. This guide explains how
each one works, what that difference protects you from, and what it doesn't.

## How password login works

You type the password. The browser sends it over TLS, and the server hashes it with
a slow function (Argon2id, bcrypt or scrypt) and compares the result with the hash
it stored when you signed up. If they match, you're in.

Three properties follow:

- **The secret travels.** Every login gives the password to whoever is receiving
  it: the real site, a phishing copy of it, a keylogger, or a shoulder-surfer.
- **It doesn't change.** A password seen once works until you change it. It still
  works next month, and on every other site where you reused it.
- **Its strength depends on you.** It's as strong as the number of guesses it takes
  to find it, which we measured in
  [How strong is your password, really?](/blog/password-strength-entropy). Leaked
  databases and reuse are why billions of passwords are on attackers' lists.

None of this is a flaw in passwords as such: it's what "something you know" means.
The fix is to add a second factor, something you have.

## How TOTP works

**TOTP** (Time-based One-Time Password, [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238)) is the algorithm behind Google
Authenticator, Microsoft Authenticator, Authy and the 2FA field of most password
managers. It has two phases.

### Setup: sharing a secret once

When you turn on 2FA, the server generates a random secret, usually 20 bytes, and
shows it to you as a QR code. The QR code contains a URI like this:

```text
otpauth://totp/WebTools:alice%40example.com?secret=JBSWY3DPEHPK3PXP&issuer=WebTools
```

The secret is the `JBSWY3DPEHPK3PXP` part, encoded in **Base32** (letters A–Z and
digits 2–7) so it can be typed by hand if the camera won't cooperate. Your app
stores it, the server stores it, and it never travels again.

### Each login: computing the code

To get the code, both sides run the same computation, independently:

1. **Time step.** Take the Unix time and divide by 30, rounding down:
   `T = floor(now / 30)`. It changes every 30 seconds, and both sides agree on it as
   long as their clocks do.
2. **HMAC.** Compute `HMAC-SHA1(secret, T)`, with `T` written as 8 big-endian bytes.
   This is the same keyed hash webhooks use, explained in
   [HMAC explained](/blog/hmac-webhook-signatures). Without the secret, nobody can
   predict the result.
3. **Dynamic truncation.** The low 4 bits of the HMAC's last byte give an offset
   (0–15). Read 4 bytes from there, clear the top bit, and you have a 31-bit number.
4. **Digits.** Keep the last 6 decimal digits: `number mod 1,000,000`.

Steps 2 to 4 are **HOTP** ([RFC 4226](https://datatracker.ietf.org/doc/html/rfc4226)), the counter-based original. TOTP only
replaces the counter with the clock.

### A worked example

[RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238) publishes [test vectors](https://datatracker.ietf.org/doc/html/rfc6238#appendix-B). Its SHA-1 secret is the ASCII string
`12345678901234567890`, or `GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ` in Base32. At Unix
time 59:

| Step | Value |
|---|---|
| Time step | `floor(59 / 30)` = 1 |
| Counter bytes | `0000000000000001` |
| HMAC-SHA1 | `75a48a19d4cbe100644e8a`**`c1397eea`**`747a2d33a`**`b`** |
| Offset | last byte `ab`, low 4 bits = `0xb` = 11 |
| 4 bytes at offset 11 | `c1397eea` & `7fffffff` = 1,094,287,082 |
| 6 digits | 1,094,287,082 mod 10⁶ = **287082** |

The RFC lists `94287082`: that's the 8-digit version of the same number. Here is
the whole computation in a few lines, with no TOTP library, in four languages:

<Tabs>
<Tab label="Shell">
```bash
#!/usr/bin/env bash
# Usage: ./totp.sh BASE32_SECRET [UNIX_TIME]
set -euo pipefail
secret=$(printf '%s' "$1" | tr -d ' =-' | tr '[:lower:]' '[:upper:]')
time=${2:-$(date +%s)}

# 1. Base32 secret -> key as hex (base32 -d wants padding to 8 chars).
while (( ${#secret} % 8 )); do secret+='='; done
key=$(printf '%s' "$secret" | base32 -d | xxd -p -c 256)

# 2. Time step -> 8-byte big-endian counter.
counter=$(printf '%016x' $(( time / 30 )))

# 3. HMAC-SHA1(key, counter).
mac=$(printf '%s' "$counter" | xxd -r -p |
  openssl mac -digest SHA1 -macopt "hexkey:$key" HMAC | tr '[:upper:]' '[:lower:]')

# 4. Dynamic truncation: offset = low 4 bits of the last byte.
offset=$(( 16#${mac: -1} ))
binary=$(( 16#${mac:offset*2:8} & 0x7fffffff ))

# 5. Keep the last 6 digits.
printf '%06d\n' $(( binary % 1000000 ))
```

```console
$ ./totp.sh GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ 59
287082
```

Needs OpenSSL 3 (`openssl mac`), `xxd` and GNU `base32`.

<Tab label="Python">
```python
import base64, hashlib, hmac, struct, time

def totp(
    secret: str,
    now: float | None = None,
    digits: int = 6,
    period: int = 30,
) -> str:
    secret = secret.replace(" ", "").upper()
    key = base64.b32decode(secret + "=" * (-len(secret) % 8))
    counter = int((time.time() if now is None else now) // period)
    mac = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
    offset = mac[-1] & 0x0F
    binary = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(binary % 10**digits).zfill(digits)

print(totp("GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ", now=59))            # 287082
print(totp("GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ", now=59, digits=8))  # 94287082
```

```go
package main

import (
	"crypto/hmac"
	"crypto/sha1"
	"encoding/base32"
	"encoding/binary"
	"fmt"
	"strings"
	"time"
)

func totp(secret string, t time.Time) (string, error) {
	secret = strings.ToUpper(strings.ReplaceAll(secret, " ", ""))
	key, err := base32.StdEncoding.WithPadding(base32.NoPadding).
		DecodeString(strings.TrimRight(secret, "="))
	if err != nil {
		return "", err
	}
	var msg [8]byte
	binary.BigEndian.PutUint64(msg[:], uint64(t.Unix()/30))

	mac := hmac.New(sha1.New, key)
	mac.Write(msg[:])
	sum := mac.Sum(nil)

	offset := sum[len(sum)-1] & 0x0f
	code := binary.BigEndian.Uint32(sum[offset:offset+4]) & 0x7fffffff
	return fmt.Sprintf("%06d", code%1_000_000), nil
}

func main() {
	code, err := totp("GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ", time.Unix(59, 0))
	if err != nil {
		panic(err)
	}
	fmt.Println(code) // 287082
}
```

```js
import { createHmac } from 'node:crypto'

const ALPHABET = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ234567'

function base32Decode(text) {
  let bits = 0, value = 0
  const out = []
  for (const char of text.replace(/[\s=]/g, '').toUpperCase()) {
    const index = ALPHABET.indexOf(char)
    if (index < 0) throw new Error(`Invalid Base32 character: ${char}`)
    value = (value << 5) | index
    bits += 5
    if (bits >= 8) {
      bits -= 8
      out.push((value >>> bits) & 0xff)
    }
  }
  return Buffer.from(out)
}

function totp(secret, now = Date.now() / 1000) {
  const counter = Buffer.alloc(8)
  counter.writeBigUInt64BE(BigInt(Math.floor(now / 30)))
  const mac = createHmac('sha1', base32Decode(secret)).update(counter).digest()
  const offset = mac[mac.length - 1] & 0x0f
  const binary = mac.readUInt32BE(offset) & 0x7fffffff
  return String(binary % 1_000_000).padStart(6, '0')
}

console.log(totp('GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ', 59)) // 287082
```

## Side by side

| | Password | TOTP code |
|---|---|---|
| What you send | The secret itself | A value derived from it |
| Valid for | Until you change it | About 30 seconds (90 with the drift window) |
| Replayable | Yes, forever | No, if the server rejects reused codes |
| Who chooses it | You (often badly) | The server, at random (160 bits) |
| Stored on the server as | A slow, salted hash | The secret itself, ideally encrypted |
| Guessing it | Offline, at billions per second if the hash leaks | Online only: 1 in 333,333 per try |
| Reused across sites | Often | Never: one secret per account |
| Stolen by a phishing page | Yes | Yes, but only usable for seconds |
| If you lose it | Reset by email | Backup codes, or account recovery |

Two lines deserve a closer look.

**Storage.** A site can hash your password because it only needs to *check* it.
It can't hash a TOTP secret, because it needs the secret itself to compute the
expected code. A database leak therefore exposes TOTP secrets in usable form unless
they were encrypted with a key kept elsewhere (a KMS or an HSM). That's the job of
the site, not yours, but it's why a 2FA secret is never something you send around.

**Guessing.** Six digits sound weak next to a 16-character password. They don't
need to be strong on their own: there's no hash to attack offline, so every guess
has to go through the login form, and the answer changes every 30 seconds.

## What TOTP stops

- **Credential stuffing.** Attackers replay leaked email/password pairs on other
  sites. With TOTP, the password alone gets them nowhere.
- **Password reuse and leaks.** A breach of one site's passwords doesn't unlock
  your account elsewhere, even if you reused the password.
- **Replay.** A code captured from your screen, a log or a network trace is dead
  within a minute, and a careful server refuses it even within that minute.
- **Weak passwords**, partly. A guessable password plus TOTP is still far harder to
  get into than a guessable password alone. It doesn't make the password safe to
  reuse, though.

## What TOTP doesn't stop

- **Real-time phishing.** A fake login page can ask for your password *and* your
  code, then type both into the real site within seconds. Kits like Evilginx
  automate this and steal the session cookie that follows. TOTP has no idea which
  site you're typing the code into.
- **Malware on your device.** If your phone or computer is compromised, the
  attacker can read the secret from the app or take the session after you log in.
- **A leaked secret.** If a site's TOTP secrets leak unencrypted, every future code
  of every account is known. The site has to reset them all.
- **Social engineering.** "We sent you a code, please read it back to confirm your
  identity" is how many 2FA-protected accounts are taken over. No legitimate support
  agent asks for the code.

<Callout type="tip" title="Passkeys close the phishing gap">
Passkeys (WebAuthn) replace the code with a signature from a key stored on your
device, and the browser binds that signature to the site's real domain. A phishing
page on another domain gets nothing it can use. Where a site offers passkeys, prefer
them. Where it offers only TOTP or SMS, take TOTP.
</Callout>

SMS codes are a weaker cousin: same 6 digits, but the code travels over the phone
network, where it can be redirected by **SIM swapping** (an attacker convincing
your carrier to move your number to their SIM). TOTP has no such channel: the code
is computed on the phone and never sent to it.

## How hard is guessing 6 digits?

A 6-digit code has 1,000,000 values. Most servers accept the previous and next code
too, to cover clock drift and slow typing, so **3 codes are valid at any moment**: a
random guess succeeds with probability 3 in 1,000,000.

That's why rate limiting is part of TOTP, not an option. With 5 tries per 30-second
window, an attacker needs about 67,000 windows on average, more than **three weeks
of nonstop guessing**, and any decent lockout or alert stops them long before. Without
any limit, a script sending a few thousand guesses per second gets in within
minutes.

## In practice

- **Turn on 2FA** on email, password manager, cloud, banking, code hosting:
  anything whose takeover would hurt.
- **Prefer passkeys**, then an authenticator app (TOTP), then SMS.
- **Save the backup codes** somewhere other than your phone. Losing the phone
  without them can mean losing the account.
- **Keep a strong, unique password anyway.** 2FA is a second lock, not a reason to
  weaken the first. A [generated password](/password) costs you nothing with a
  password manager.
- **Never read a code to anyone.** It's only ever typed into the site you're logging
  in to.

## For developers

Computing a code is the easy part. Accepting one safely needs four more things:

- **A drift window**: accept `T-1`, `T` and `T+1`, no wider.
- **Constant-time comparison**, so the response time doesn't leak how many digits
  matched.
- **Single use**: store the last time step accepted for each user and refuse any
  code at or below it.
- **Rate limiting** per account, as computed above.

Building on the `totp` function from the worked example:

<Tabs>
<Tab label="Shell">
```bash
# verify.sh BASE32_SECRET CODE LAST_COUNTER
# Prints the matching time step (store it as LAST_COUNTER) or exits with 1.
secret=$1 code=$2 last=$3
now=$(date +%s)
current=$(( now / 30 ))
for counter in $(( current - 1 )) $current $(( current + 1 )); do
  expected=$(./totp.sh "$secret" $(( counter * 30 )))
  if [[ $expected == "$code" ]] && (( counter > last )); then
    echo "$counter"
    exit 0
  fi
done
exit 1
```

Fine for a test, not for production: Bash string comparison stops at the first
difference, and there's nowhere to keep state or rate limits.

<Tab label="Python">
```python
import hmac

def verify_totp(
    secret: str,
    code: str,
    last_counter: int,
    now: float | None = None,
) -> int | None:
    """Return the matching time step, or None.

    Store it as the new last_counter, so the same code can't be used twice.
    """
    now = time.time() if now is None else now
    current = int(now // 30)
    match = None
    for counter in (current - 1, current, current + 1):
        expected = totp(secret, now=counter * 30)
        # compare_digest takes the same time wherever the strings differ.
        is_valid = hmac.compare_digest(expected, code)
        if is_valid and counter > last_counter and match is None:
            match = counter
    return match
```

```go
import "crypto/subtle"

// verifyTOTP returns the matching time step. Store it and pass it back as
// lastCounter next time, so the same code can't be used twice.
func verifyTOTP(secret, code string, lastCounter int64, now time.Time) (int64, bool) {
	current := now.Unix() / 30
	var match int64
	found := false
	for counter := current - 1; counter <= current+1; counter++ {
		expected, err := totp(secret, time.Unix(counter*30, 0))
		if err != nil {
			return 0, false
		}
		if subtle.ConstantTimeCompare([]byte(expected), []byte(code)) == 1 &&
			counter > lastCounter && !found {
			match, found = counter, true
		}
	}
	return match, found
}
```

```js
import { timingSafeEqual } from 'node:crypto'

/** Returns the matching time step, or null. Store it as the new lastCounter. */
function verifyTotp(secret, code, lastCounter, now = Date.now() / 1000) {
  const current = Math.floor(now / 30)
  let match = null
  for (let counter = current - 1; counter <= current + 1; counter++) {
    const expected = Buffer.from(totp(secret, counter * 30))
    const given = Buffer.from(code)
    // timingSafeEqual throws on different lengths, so check that first.
    const ok = given.length === expected.length && timingSafeEqual(given, expected)
    if (ok && counter > lastCounter && match === null) match = counter
  }
  return match
}
```

Each loop checks all three steps even after a match, so the response time doesn't
depend on which one matched. In production, use your platform's maintained library
(`pyotp`, `pquerna/otp`, `otpauth`): the point of writing it by hand here is to see
there's no magic.

A few more rules for the server side:

- **Generate secrets with a CSPRNG**, 20 bytes, one per account. Never derive them
  from the user ID or anything guessable.
- **Encrypt secrets at rest** with a key that isn't in the same database.
- **Ask for a code during setup** before turning 2FA on, to prove the user's app has
  the right secret and a correct clock.
- **Issue backup codes** at the same time: 8 to 10 single-use random codes, stored
  hashed like passwords. The [password generator](/password) can make them.
- **Stick to SHA-1, 6 digits and 30 seconds** in the `otpauth://` URI. The RFC allows
  more, but several popular apps ignore those parameters and show wrong codes.

### Why the TOTP tool has no API

Every other tool on this site comes with a REST endpoint and an MCP tool. The TOTP
generator deliberately doesn't. Whoever holds a TOTP secret can produce every
future code of that account, so a secret should only ever exist in the user's
app and on the site that issued it. An endpoint that takes a secret and returns a
code would invite people, and AI agents, to send real secrets to a third party.
The page computes everything in your browser and never sends the secret anywhere.
For anything automated, the twenty lines above are all you need.
